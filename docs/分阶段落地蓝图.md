# 六大能力扩展 · 分阶段落地蓝图

> 目标：把「单机上传文件分析」升级为「数据自动进来、多门店并行、主动推送」的 SaaS。
> 原则：**保留现有亮点不动**——双入口、一键复制微信、行动清单闭环率、清洗体检可回滚、白话统计解释。

## 一、本次已落地（可直接跑）

### 1. 数据接入（骨架 + 示例连接器）
- **实现位置**：`datasources.py`（抽象层 + SQLite 持久化）、`connector_sqlite.py`（示例连接器）、`sources_ui.py`（入口页 + 通用接口配置表单）
- **数据结构**：
  - `DataSource` 抽象基类：`fetch(since)` / `health()` / `normalize()`，`since` 是增量游标
  - 标准三表字段约定：销售明细（`SALES_COLS`）、库存快照（`INVENTORY_COLS`）、会员（`MEMBER_COLS`）
  - 本地 SQLite（`data/stores.db`）：`sources`（游标）、`snapshots`（数据快照）、`stores`/`users`/`subscriptions`/`jobs`
- **交互方式**：侧栏「1. 数据来源」用 radio 在「上传文件 / 连接数据源」间切换——**和上传表格并列**。
  选「连接数据源」→ 通用配置表单（数据源类型下拉 + 接口地址/AppKey/门店号等字段）→ 点「连接并拉取」→ 数据落库并**直接喂给现有分析链路**（清洗、双入口、图表、导出全复用）。
- **现状**：SQLite 示例连接器可跑通全链路；`api_generic`（通用 HTTP 接口）是预留位，填了会明确提示「需厂商开放 API 后接入」，不画假入口。

### 2. 自动跑批与预警（纯函数 + 本地推送）
- **实现位置**：`scheduler.py`
- **数据结构**：订阅（`subscriptions` 表：用户/topic/渠道/规则）、结论（severity/title/detail/action）、推送渠道（`CHANNELS`：local 已实现，wecom/email 预留）
- **交互方式**：`sources_ui` ③ 手动跑批 → 生成异常预警 + 日报 → 落 `output/notifications/`
- **现状**：跑批是纯函数，可由任意调度器触发；真企业微信推送待接 adapter

### 3. 多门店 / 权限（结构 + 隔离 + 对比）
- **实现位置**：`stores.py`
- **数据结构**：门店树（`code/name/region/parent`）、角色（`boss/region_manager/store_manager`）、可见范围（`scope`）
- **交互方式**：`sources_ui` ② 演示跨店对比；`visible_codes()` 做数据隔离
- **现状**：纯逻辑已可单测；真实登录/会话认证待接后端

### 4. 预测补货增强（动态安全库存）
- **实现位置**：`inventory.py`（新增 `safety_stock()` + `_robust_std()`）
- **算法**：安全库存 SS = z·σ_daily·√lead，σ 用 MAD 剔除极端日后的稳健标准差；生鲜封顶防压货
- **效果**：波动大→SS 高，含 500 元大单→被 MAD 剔除、SS 不被拉爆（已实测）
- **现状**：已并入 `sku_summary` 订货公式，`reorder_explain` 同步更新，测试已更新

### 5. 口径语义层 / 指标中心
- **实现位置**：`metric_catalog.py`
- **数据结构**：`CATALOG`（指标→公式模板/单位/类型/口径说明/别名），`bind_columns()` 把语义占位符绑到实际列名
- **效果**：「定义一次，适配多数据源」，报告/字典/推送从同一份定义取口径
- **现状**：已可被 `MC.dict_rows()` 调用；与 `metrics.py`（执行器）分工明确

### 6. 规模性能
- **实现位置**：`scale.py`
- **能力**：`read_csv_chunked()`（分块读）、`duckdb_query()`（惰性查询大数据）、`basket_vectorized()`（万级 SKU 购物篮向量化）、`downcast()`（数值降精度省内存）
- **现状**：作为可选加速路径，不侵入主链路

## 二、数据结构全景

```
data/stores.db (SQLite)
├── sources       数据源：key / label / config / last_sync(增量游标)
├── snapshots     数据快照：source_key / kind(sales|inventory|members) / fetched_at / payload
├── stores        门店树：code / name / region / parent
├── users         用户：id / name / role / scope(可见范围)
├── subscriptions 订阅：user_id / topic / channel / rule(JSON)
└── jobs          定时任务：name / schedule / source_key / enabled
```

标准数据表字段（连接器输出统一对齐）：
- 销售明细：订单号/日期/时间/SKU/名称/品类/数量/单价/金额/成本/会员编号/门店编码
- 库存快照：SKU/名称/品类/期末库存/在途/保质期天/单位成本/门店编码/日期
- 会员：会员编号/最近购买/购买频次/累计金额/门店编码

## 三、分阶段落地顺序（优先打通数据接入）

### 阶段 0（本次已完成）：骨架验证
- 数据源抽象层 + 示例连接器 + 多门店模型 + 跑批预警 + 安全库存 + 语义层 + 规模优化全部跑通。
- 交付物：7 个新模块 + 2 个测试（`test_new_modules.py` 全绿，`test_checks.py` 全绿）。

### 阶段 1（下一步，最优先）：打通一个真实数据源
- **为什么最优先**：手动上传是当前唯一的死结——老板不会每天导文件。数据接进来，后面 2/3/6 才有真实数据可跑。
- 动作：选一家收银系统（银豹/客如云/有赞/科脉），确认其开放 API 与字段，照着 `connector_sqlite.py` 写一个 `connector_xxx.py`，把 `fetch()` 换成「HTTP 调用 + 鉴权 + 字段映射」；同时在 `sources_ui.SOURCE_TYPES` 里加一项，前端就能选它、填它的 AppKey/门店号。
- 验收：能增量拉取销售/库存/会员，字段对齐标准表，落 SQLite 可查。

### 阶段 2：定时调度 + 推送
- 动作：用操作系统计划任务 / cron 触发 `scheduler.py` 的跑批函数；接一个企业微信 webhook 作为 `deliver()` 的 wecom 实现。
- 验收：每天固定时间自动生成日报 + 异常预警，推到店长手机，无需打开网页。

### 阶段 3：多租户与后端
- 动作：把本地 SQLite 换成云数据库（或 WorkBuddy 云服务），加登录/会话，`users.scope` 做数据隔离，`stores.py` 的可见范围逻辑复用。
- 验收：店长登录只见自己店、区域经理见本区、老板见全部，跨店对比自动按权限过滤。

### 阶段 4：规模与预测深化
- 动作：万级 SKU 时用 `scale.duckdb_query` 替代 pandas 全量加载；安全库存接入真实库存快照（替换 `inventory.py` 的仿真）；可选引入需求预测模型（天气/节假日/促销特征）。
- 验收：10 万行级数据秒级出概览；生鲜订货在波动场景下缺货率下降。
